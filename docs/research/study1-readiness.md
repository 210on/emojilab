## 1. いまの方針

- 研究者は、Yahoo!クラウドソーシングの研究室アカウント、外部調査サイト、完了コードによるポイント付与を利用する方針を検討している。
- 募集サービス側で指定できる場合は、PCからの参加に限定する。申請書の対象はデスクトップPCまたはノートPCで、スマートフォン・タブレットは対象外。
- 実験画面でもPC利用とブラウザ倍率100%を参加者に確認してもらう案。端末の自動判定だけで機種を確実に識別できるとは限らない。
- 現時点ではスクリーンショットや画面写真を収集せず、申請内容との関係、必要性、説明・同意と管理方法を研究責任者・倫理審査窓口に確認する。スクリーンショットは動画・画面録画と必ずしも同義ではないが、新たな画面画像収集が承認済みであるとは判断できない。
- 研究者が所有するPC等での**合成データによる内部テスト**は、本番参加者の募集・回答収集と区別する。本番または予備調査への参加者募集は、必要な手続きの確認後に行う。

## 4. 本番フロー案

1. Yahoo!上の募集説明から外部の調査画面へ移動。対象条件・所要時間・ポイントの条件を説明する。
2. 研究目的、収集項目、参加の任意性、回答拒否、中止、撤回方法、保管・連絡先、報酬を、承認された説明文に沿って表示する。**同意前に研究データを保存しない**運用を含めて確認する。
3. 同意後、申請書に基づく参加条件と表示方法を確認。対象外または参加をやめる場合の案内・ポイントの扱いを事前に定める。
4. 撤回用IDを表示し、参加者が保存できるようにする。研究データと完了コードは別の用途として扱い、対応表の保存先・保持期間・削除方法を明確にする。個人特定の必要な情報は収集しない。
5. 決定したリストを均衡割り付けし、固定版の15刺激をランダム順に提示。各画像は32×32 CSS pxでライト・ダークに並べる。回答の拒否や欠測の扱いは事前に定める。
6. 回答を保存し、サーバー側の保存成功と完了状態の確認後に完了コードを表示。ネットワーク失敗・再送・重複操作・不正な再利用への対応を決める。
7. 参加者がYahoo!側に完了コードを入力。研究用ID・撤回用ID・報酬のコードは不用意に同一にせず、撤回と報酬をどう両立するか検討する。
8. 承認内容に基づき、撤回期間内の削除と、期限後の対応情報の破棄を行う。外部事業者が保持する情報の削除可能範囲を過大に約束しない。

現行画面はCSV / JSONダウンロードとlocalStorage保存であり、上記のサーバー回収・完了コード・撤回処理は実装済みではない。

## 5. 実験前の点検項目

### 刺激・表示

- [ ] 刺激、正答・意味、色・線・フォント、背景、指標バージョンを決め、画像ファイルとハッシュを保存した。
- [ ] 全刺激の実際の描画文字と正答／意味欄が一致することを目視確認した。
- [ ] 32 CSS pxが実際の画像要素に適用され、表示と記録に差がないことをPC・ブラウザで確認した。
- [ ] 背景が両方同時に表示され、余白・位置・縮小方法・画像品質を揃えた。
- [ ] 参加者・語句・刺激条件・提示順の割り当て表をシミュレーションし、予定される各セルを数えた。
- [ ] ブラウザのズームや端末の表示設定を参加者にどう案内し、画面途中の変更をどう扱うか決めた。

### 同意・回収

- [ ] 適用される承認通知・変更内容・募集方法・質問項目・説明文を確認した。
- [ ] 対象者、休憩、中止、回答拒否、撤回期限、連絡先とポイントの説明が実際の運用と一致する。
- [ ] サーバー保存・ID・完了コードの生成、送受信、アクセス制限、削除、保存期間を確認した。
- [ ] ネットワーク断、再送、二重送信、途中離脱、回答拒否、撤回を合成データで試した。
- [ ] 研究者が結果を集約でき、参加者の画面には不要な他者の情報が表示されない。

### 予備テスト・分析

- [ ] 説明の理解度、実際の所要時間、疲労、回答率、実表示の問題を確認した。
- [ ] 床・天井効果、画像条件の欠測、語句の偏りを確認した。
- [ ] 分析の主要項目、主な比較、欠測・除外、自由記述の採点、補助分析を固定した。
- [ ] 約100人で得られる推定精度を条件・参加者・語句のばらつきに基づいて検討した。
- [ ] 本番では刺激とスコアを途中変更せず、変更が必要な場合の中断・手続きを定めた。
